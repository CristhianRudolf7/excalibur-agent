# Native PDF extraction

The `internal/docextract/pdf` package implements the shared document extractor
and renderer for Sections 10.9, 13, 14.4, 14.7 and 17. It uses PDFium embedded as
WebAssembly through `github.com/klippa-app/go-pdfium` v1.21.4 and wazero v1.12.0.
The backend adds no CGO requirement or external executable dependency.

Use `pdf.New(pdf.Options{})` as both `docextract.Extractor` and
`docextract.Renderer`. The default backend invokes the current Excalibur binary
as `internal pdf-worker`, a private command omitted from help. Each extraction
owns one worker and a private temporary input file, deleted on return. Worker
requests and replies are JSON lines. A Wasm instance is reused for a document and discarded after any failed
request; compiled Wasm is cached in the user cache directory and reused across
workers. No PDF JavaScript or form actions
are invoked. The Wasm filesystem has no host mounts.

The parent bounds input to 64 MiB, documents to 2,000 pages by default, each
page to 30 seconds, and each document to 10 minutes. Wasm linear memory has a
hard 512 MiB limit; the parent samples child RSS every 100 ms and terminates its
process group above 1 GiB. RSS monitoring is a sampled limit, so brief overshoot
is possible. Linux race builds allow 2 GiB for instrumentation overhead; release
builds retain 1 GiB. Explicit `Options.MemoryLimit` values apply unchanged in
every build. `Options` can override timeouts, RSS limit, executable path, and
platform collaborators. Production workers use native Linux, Windows and macOS
process control and RSS samplers; unsupported operating systems return
`errors.ErrUnsupported`. macOS uses the interpreter for race builds
and compiler mode otherwise; native execution still requires target-OS checks. `Options{InProcess:true}` is for tests and
uses Wasm context cancellation without process isolation.

Native results include title, author, physical page count, page labels,
bounded bookmark traversal, text blocks and top-left point coordinates.
Text is ordered by columns and vertical position, joined across hyphenated line
breaks, and merged into paragraphs using vertical gaps. Running matter repeated
at the same vertical band on a majority of selected pages is removed. Page
number normalization applies in the top/bottom margins. Printed
contents pages are dropped with `toc_page`. Quality is assessed before cleanup,
so removing running matter or contents does not trigger redundant OCR.

Quality combines the fraction of non-garbled characters, character density per
page area, and image coverage. Private-use, replacement, control, surrogate,
unassigned characters and literal CID placeholders reduce quality. Invisible
text is assessed as native text, preserving useful existing OCR layers. Call
`pdf.PageNeedsOCR` to apply the configured quality threshold. This package never
calls a model or performs OCR itself.

PNG rendering accepts 72–300 DPI (zero selects 150) and rejects images above
12 million pixels before allocating a bitmap. Encrypted files return
`pdf.ErrEncrypted`; input, page-count and render limits use `pdf.ErrTooLarge`.
A worker crash, page timeout or memory overrun produces a failed-page warning;
the next page starts a replacement worker. Document cancellation returns the
context error and terminates the worker. Other damaged pages are read on a
best-effort basis and can yield empty native text for the ingester to OCR.

Fixtures are generated by `internal/docextract/pdf/testpdf`, including encrypted
PDFs, Unicode maps, images, page labels and bookmarks. Package tests exercise
native extraction, rendering, cleanup, quality, cancellation and simulated
worker crash/hang recovery. They use no models or paid services.

## Verification

The generated-fixture suite passes with the race detector and a 3 GiB memory
cap. The command package's race suite passes, and
`TestPDFWorkerIsHiddenAndReadsDocument` exercises the real hidden entrypoint
with a child copy of the test executable. There are no live API calls.

Verified commands (Go commands run at nice 19, with `-p 2` and
`GOMAXPROCS=2`; tests run in a `MemoryMax=3G`, `MemorySwapMax=0` user scope):

- `go test -race -count=1 -timeout 300s ./internal/docextract/pdf/...`
- `go test -race -count=1 -timeout 180s ./cmd/excalibur`
- `go test -race -count=1 -timeout 90s -run TestPDFWorkerIsHiddenAndReadsDocument ./cmd/excalibur`
- `go vet ./...`
- `go build ./...`, including `GOOS=darwin` and `GOOS=windows`
- `CGO_ENABLED=0 go build ./internal/docextract/pdf/...`
- `staticcheck ./internal/docextract/pdf/... ./cmd/excalibur`
- `gofmt -l .` (empty) and `scripts/check-no-bare-go.sh`

Initial cold compilation and an unnecessarily large render fixture exceeded
short test deadlines on the heavily loaded shared host. Persisted Wasm
compilation caching, document-level instance reuse and small generated render
fixtures resolved those failures. The final PDF race suite completed in 93
seconds on that host, while the production-entrypoint check took 4 seconds.

## Linux cold-worker memory verification

The Linux parent enforces the worker budget by polling
`platform.LinuxResourceSampler` every 100 ms. RSS comes from the child's
`/proc/<pid>/status` `VmRSS`, converted from KiB to bytes. This budget uses
neither `RLIMIT_AS` nor cgroup-wide memory consumption; the sampler's separate
cgroup OOM/process counters do not determine termination. The 512 MiB Wasm
linear-memory cap also does not bound compiler allocations or race shadow
memory in the host process.

`TestPDFWorkerIsHiddenAndReadsDocument` launches the command test executable
itself, including its race runtime. On Linux, cold native compilation of
PDFium in that executable exceeds the production RSS budget. A warm disk
compilation cache can conceal the failure. The test now gives the child a
fresh `XDG_CACHE_HOME` and allows three minutes for cold compilation while
other verification packages compete for CPU. Linux race builds keep the native
compiler and use a 2 GiB default worker budget. Other builds, explicit budgets,
and Wasm limits are unchanged.

Local Linux/amd64 measurements with Go 1.27.3, `GOMAXPROCS=4`, affinity to four
CPUs, a fresh Wasm cache for each run, and the generated one-page text PDF:

| Worker | Peak sampled RSS | Result |
| --- | ---: | --- |
| Original command race executable, 1 GiB budget | 1,024.0 MiB | Killed during compilation; unchanged command test also reproduced the CI error |
| Same race executable, explicit 2 GiB budget | 1,175.6 MiB | Extracted title and exact page text in 39.7 seconds |
| Release executable with embedded web UI | 407.6 MiB | Extracted title and exact page text in 6.8 seconds |
| Same release executable under CPU and allocation load | 419.3 MiB | Extracted title and exact page text in 8.1 seconds |

The release executable was built after `make web`, using `CGO_ENABLED=1`,
`-tags=sqlite_fts5`, `-trimpath`, and `-ldflags '-s -w -X main.version=ci2-local'`,
matching the native Linux release recipe. Its file size was about 85 MiB.
Extraction used `pdf.New` with that executable as `WorkerPath`, the real Linux
sampler, and the default 1 GiB limit. The load run used a `MemoryMax=2G`,
`MemorySwapMax=0` user scope and three additional processes, each touching
256 MiB continuously, all on the same four CPUs. Binary size alone does not
imply resident memory, and the release worker stayed within its budget even
with slower cold startup. These fixture measurements do not guarantee that
every PDF will fit; oversized workers are still terminated.

The fixed cold command test also passed in a `MemoryMax=3G`,
`MemorySwapMax=0` user scope with the same four-CPU affinity (43.2 seconds).
The PDF package race suite passed with `-p 2 -count=1`. This investigation did
not add native Windows or macOS verification.
